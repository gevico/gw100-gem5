# 共享 SRAM 规格（spec-sram）

版本为 0.1，面向模型、固件和后续 RTL 实现。规范拥有共享存储器的组织、
服务时序、ECC 和生命周期。管理 Tile、Compute Tile 各自拥有地址、权限、
寄存器和任务语义。

## 1. 档案与精度

单一真源为 spec-src/sram/gw100-sram.json。生成 C、C++、Python 定义，
构建前执行 make sram-spec-check。通用微架构参数的数字行为由独立检查器
验收，厂商宏的物理可实现性由后续宏选型及 STA 验收。

| 参数 | management | compute_1rw | compute_1r1w |
|---|---|---|---|
| 数据容量 | 2 MiB | 2 MiB | 2 MiB |
| bank | 8 | 16 | 16 |
| 宏数据字 | 8 B | 16 B | 16 B |
| 地址分布 | 连续 bank 分区 | 按宏字交织 | 按宏字交织 |
| 物理端口 | 1RW | 1RW | 1R1W |
| 来源数 | 3 | 5 | 5 |
| 每来源事务槽 | 8 | 8 | 8 |
| 读延迟、写提交延迟、II | 各一周期 | 各一周期 | 各一周期 |
| 正常时钟周期 | 2000 ps | 1000 ps | 1000 ps |
| 启动时钟周期 | 40000 ps | 1000 ps | 1000 ps |
| 写掩码粒度 | 8 B | 8 B | 8 B |
| ECC | 64+8 SECDED | 64+8 SECDED | 64+8 SECDED |

bank 数为二的幂，宏数据字支持 8、16、32、64 B，写掩码粒度为整除宏字的
二的幂。每 bank 至少容纳一个宏字。地址计算使用实例内偏移。
连续分区的 bank 为 offset / (size / banks)。
交织的 bank 为 (offset / word_bytes) % banks。各实例的内容和资源独立。

管理正常带宽的阵列上限为 32 GB/s，Compute 1RW 为 256 GB/s，均为读写合计。
Compute 1R1W 的每个方向各为 256 GB/s。实际吞吐受逻辑入口、返回和竞争约束。
这些上限由 bank、字宽、时钟及 II 推算。

## 2. 接口、资源与准入

每个逻辑入口最多每周期接受一笔 1–64 B 请求，最多每周期交出一笔响应。
来源由物理连接绑定。每个来源有八个父事务槽，持有请求数据、返回数据及
拆分描述符，直到返回被上游接受。转发适配器持有的返回额度也计入准入。

每事务数据预留为 64 B 请求和 64 B 响应。拆分描述符上限为九个宏字，
覆盖最大请求及其未对齐边界。队列元素、活动操作和初始化流水均从有限的
事务与配置上限推导。队满通过 retry 反压。

| 资源 | management | Compute 档案 |
|---|---|---|
| 数据阵列 | 2,097,152 B | 2,097,152 B |
| ECC 存储 | 262,144 B | 262,144 B |
| 父事务槽 | 24 | 40 |
| 请求及响应数据预留 | 3,072 B | 5,120 B |
| 单事务拆分上限 | 9 项 | 5 项 |
| 来源与 bank 的操作队列 | 24 | 80 |

描述符和队列索引均由父槽数量约束，每事务最多保留上述拆分项。
C++ 容器、指针与对象布局属于仿真开销，RTL 元数据位宽由实现规格核算。

单请求预检地址、长度和字节使能。mask 的 bit i 对应请求内字节 i。
边界与非法掩码错误在数据效果发生前报告。未就绪请求返回明确错误。
阵列访问按宏字拆分，宏字内自然对齐的 8 B 单元不可撕裂。

内部完成结果包含事务号、复位代次、状态、读数据和已提交字节掩码。
状态包含 OK、地址错误、未就绪、ECC UE、复位和部分效果故障。
执行中故障保留已发生效果，适配层按所属协议转换。

## 3. 周期与顺序

全局 tick 为 1 ps，时钟使用 gem5 实际量化后的周期。trace 分别记录
accept、issue_read/issue_write、sample、commit、ready、response。
accept 为阵列队列准入，上游传输到达和适配器接受时点单独统计。
transport 事件保存 upstream_accept 与 arrival，分别对应上游准入及
headerDelay、payloadDelay 结束，便于分离入口传输和阵列等待。

一个边沿依次处理复位与门控、已有操作到期、队列准入、仲裁和新发出。
读在发出边沿采样，发出后 read_cycles 个有效边沿返回。写在发出后
write_cycles 个有效边沿提交，随后成功完成。响应阻塞持续占用返回额度。
宏字锁从写或 RMW 发出持有至写提交。读采样后的返回流水可与后续操作重叠。

每 bank 每来源一个有界操作 FIFO，轮询选择队首操作。1RW 共用端口，
1R1W 可同时处理不同宏字的读和写。同宏字的碰撞由控制器串行化。
RMW 读取到期后优先完成其写阶段，该阶段占用真实写端口与 II。
同来源的同 bank 发出保持队列顺序，所有读写满足 spec-address-map §6。
来源排空覆盖此前请求及返回接受，作为 fence 的目标完成接口。
外壳的 sourceDrained 和 drainedMemory 同时覆盖传输等待、阵列请求与
返回反压。initialize 通过 Ready 状态通知清零完成，保持进入返回成功状态。

### 3.1 仲裁保证

bank 队首操作满足前序地址依赖并已预留返回资源时开始计算仲裁等待。
入口排队、地址依赖与返回等待另计。其他来源的端口占用计入仲裁等待。

management 的三个来源均为一周期基础访问，RMW 最多连续占两个服务机会。
保守界取来源数乘以最长 RMW 服务占用，为六周期，满足既定 16 周期要求。
该界要求时钟正常运行、操作具备执行条件。来源内部排队和下游接收暂停
按各自统计口径报告。改变档案时重新检查这个推导和压力测试。

## 4. ECC 与错误

每 64 位数据配置八位偶校验。Hamming 位置 1–71 中，1、2、4、8、16、
32、64 为七个校验位，其余按数据 bit 0–63 顺序填入。第八位为整体偶校验。
故障注入编号 0–63 为数据位，64–70 为上述七个校验位，71 为整体校验位。

完整 ECC 字写重新编码。部分 ECC 字或不足宏掩码粒度的写执行 RMW，
持有宏字锁，读延迟与写延迟分别计量。完整码字写可覆盖原有故障。
CE 纠正值用于读返回，普通读保持阵列原始故障，后续 RMW 可将纠正值写回。
UE 的 RMW 对应宏字保持原值。多宏字请求发现 UE 后停止尚未发出的操作，
已发出的写按实际情况完成，已提交掩码用于区分无效果和部分效果。

管理 CE/UE 事件接入现有状态、计数、阈值、地址和 PLIC 源。
同 tick 硬件置位优先于软件清除。首次 UE 同 tick 多地址取最小地址。
CPU UE 为访问错误，ML 读和单 ECC 字 RMW 写使用现有 REJECT 契约。

## 5. 初始化、复位与恢复

初始化每 bank 并行发出清零写，遵守写 II，实际提交时写入零及正确 ECC。
最后一笔初始化写提交后才进入 Ready。以首次发出为起点，清零时间为
（每 bank 字数 − 1）× II + write_cycles 个周期。
management 在 25 MHz 的参考耗时为 1.31072 ms。

Reset、Initializing、Ready、Retention 为存储状态。排空包含入口、
活动操作和返回接受。保持进入要求排空，退出恢复已保存的数据和 ECC。
时钟暂停冻结剩余有效周期，恢复后使用实际新时钟边沿继续。

复位先于同 tick 写提交，取消未提交写。旧响应恰好完成一次，或由已退役
来源的适配层完成内部收尾。管理冷、热、设备完全复位重新清零，FLR 保留。
Compute 功能复位保留数据与 ECC，外部请求先排空。
初始化期间的保留复位重新开始清零，完成前继续保持 Initializing。
保持期间的保留复位继续保持 Retention，仍需显式退出。

组件 checkpoint 要求 Ready 或 Retention 且排空，保存数据、ECC、代次、
事务号、统计及仲裁状态，校验组织指纹。管理 Tile 的整机状态归整机恢复关口。
atomic 与 functional 为兼容和调试访问，使用排空后的相同数据与 ECC 存储。

## 6. 验证入口

- make sram-spec-check 检查共享定义、参数与固件链接布局。
- make sram-test 运行组件、独立参考、gem5 夹具与软件能力矩阵。
- tools/sram_verify.py 使用独立 Python 字节数组和时序、带宽公式。
- gem5-ext/configs/sram_fixture.py 验证真实 timing 端口、返回阻塞、
  多引擎、CE/UE、Ready/Retention 文件 checkpoint。

性能预热 10 µs、测量 100 µs，合法确定性事件误差最多一 tick，
独立吞吐参考偏差最多 ±1%。记录档案、实际周期、种子、源码与二进制指纹。
验证记录在同目录 spec-sram/verification.md。
