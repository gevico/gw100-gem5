## 1. 概述

### 1.1 范围

本文档定义：

- DPA 空间的划分：设备内存、各 Tile 的窗口、Tile 本地窗口；
- 设备内存地址在各通道之间的交织；
- 每个 initiator 能访问哪些区域，以及由谁检查；
- 设备内部的内存模型：访问粒度、原子性、写入序、可见性、fence 和同步。

下列内容不在本文档范围内：

- 各 Tile 寄存器区内部的布局，由各部件的规格定义：`spec-compute-tile`（待写）、`spec-dram`（待写）、`spec-mgmt-tile`；
- 管理 CPU 的本地地址空间，见 `spec-mgmt-tile` §3.3；本文档只定义它看到的 DPA 部分；
- host 侧的地址：BAR 的划分见 `spec-pcie` §5，host 内存的总线地址由驱动交给设备，不进入 DPA 空间；
- NoC 的报文格式、路由、流控和死锁避免，将由 `spec-noc`（待写）定义；同步原语将由 `spec-tile-sync`（待写）定义。

### 1.2 约定

- 规范用语"必须""应""可"和"TBD"的含义与其他规格相同；TBD 列入 §9。
- 地址写作 `0x10_0000_0000`，下划线只为便于阅读。区间写作 [起, 止)。
- 带点号的名字（如 `addr.device_pa_bits`）是架构参数。§10 只给出本文档拥有的参数的取值，其他参数写明由哪份规格定义。
- 引用尚未编写的规格时标"（待写）"，表示相关行为还没有规范性定义。

### 1.3 术语

| 术语 | 全称 | 含义 |
|---|---|---|
| DPA | Device Physical Address | 设备内部所有 initiator 共用的物理地址，宽度 `addr.device_pa_bits` = 40 位（§3） |
| initiator | — | 在某个接口上发起读写的一方。未加限定时指 NoC 上的 initiator，即在 NoC 上发起读写的部件：管理 CPU、HDMA、BAR2 调试窗口、Compute Tile 的 Data Mover。与 PCIe 的 requester（`spec-pcie` §1.4）属于不同层次 |
| target | — | 处理读写并返回响应的部件：Memory Tile、Compute Tile 的 SRAM 和寄存器、管理 Tile 的事件寄存器和开放的 SRAM 区间。与 PCIe 的 completer 属于不同层次 |
| NI | Network Interface | 每个 Tile 连接 NoC 的接口：initiator 一侧做源端区域检查、算出目标坐标；target 一侧接收请求、返回响应 |
| 请求 | request | initiator 发到 NoC 上的一次读或写，可以是单次访问，也可以是突发（§6.1） |
| OK、REJECT、FAULT | — | 请求的三类响应：已执行完毕 / 没有任何效果 / 效果未知（§6.3 规则 0） |
| 访问粒度 | — | 单次访问与请求的大小、对齐和跨界规则（§6.1） |
| 不可撕裂 | single-copy atomic | 自然对齐、不超过 8 B 的单次访问在 target 处作为一个不可分割的操作执行（§6.1） |
| 生效 | performed | 写在 target 处完成；此后 target 处理的对同一地址的读，返回这次写的值或写入序中更晚的值（§6.3 规则 5） |
| fence | — | 本规格定义的 initiator 级屏障：等待本 initiator 此前发出的全部请求完成后，才发出之后的请求（§6.3 规则 6）。不同于 host CPU 或驱动中的内存屏障 |
| RMW | Read-Modify-Write | 读出、修改一部分、再写回。本规格中只指 target 为不足一个 ECC 字的写所做的内部操作（§6.1）；v0.1 不提供软件可发起的原子 RMW |
| 地址交织 | interleaving | 按地址把设备内存分布到不同通道的映射（§3.2） |
| Tile 窗口 | tile window | 每个 Mesh 位置在 DPA 空间中的 16 MiB 地址范围（§4.1） |
| Tile 本地窗口 | local window | Compute Tile 内部访问时指向本 Tile 窗口的 DPA 范围（§4.3）；与管理 CPU 的本地地址（`spec-mgmt-tile` §1.3）不同 |
| 受保护区域 | protected region | 设备内存中只有管理 CPU 能访问的地址范围（§5.3） |
| HDMA、Data Mover | — | 见 `spec-arch` §1.4 |
| 管理 CPU | — | 见 `spec-mgmt-tile` §1.3 |

## 2. 设计决策

### 2.1 单一的平坦物理地址空间，宽 40 位

- **决定**：设备内部只有一个物理地址空间，`addr.device_pa_bits` = 40 位（1 TiB），所有 initiator 用同一套地址；不做地址翻译。
- **理由**：
  - 40 位足以容纳 64 GiB 的设备内存区域和 64 个 Tile 窗口，还留有大量空间。
  - 更宽的地址会增加 NoC 报文头、描述符和寄存器的位宽，而 v0.1 用不到。
  - 不做翻译，与"区域保护、不使用 MMU"的决策一致（`spec-arch` §2.5）。
  - 已删除的参数草案 v0.2 用的是 48 位，二者的差异见附录 A。

### 2.2 每个 Tile 一个固定大小的窗口，按坐标编址

- **决定**：每个 Mesh 位置分配一个 16 MiB 的窗口，窗口编号由坐标计算；窗口的前半部分是 SRAM，后半部分是寄存器。
- **理由**：
  - NoC 可以直接从地址算出目标坐标，不需要查表，复位后就能路由。
  - 编号按 8 × 8 的网格计算，Mesh 扩大到 8 列 × 8 行之前，现有 Tile 的地址都不变。

### 2.3 Tile 本地窗口

- **决定**：保留一段 Tile 本地窗口：Compute Tile 内的部件访问这段地址时，指的是执行这次访问的 Tile 自己的窗口。本地窗口只在 Tile 内部译码，不出现在 NoC 上。
- **理由**：一条张量级指令可以多播给多个 Tile（`spec-arch` §2.3）。指令中的 SRAM 操作数如果写成全局地址，就只能指向某一个 Tile；写成本地窗口中的地址，同一条指令在每个 Tile 上都访问各自的 SRAM。

## 3. 地址空间

### 3.1 总表

| DPA | 大小 | 内容 |
|---|---|---|
| 0x00_0000_0000 – 0x0F_FFFF_FFFF | 64 GiB | 设备内存区域。[0, `dram.size`) 是已安装的设备内存；其余部分保留 |
| 0x10_0000_0000 – 0x10_3FFF_FFFF | 1 GiB | Tile 窗口：64 个，每个 16 MiB（§4） |
| 0x10_4000_0000 – 0x1F_FFFF_FFFF | | 保留 |
| 0x20_0000_0000 – 0x20_00FF_FFFF | 16 MiB | Tile 本地窗口（§4.3），只在 Compute Tile 内部有效 |
| 0x20_0100_0000 – 0xFF_FFFF_FFFF | | 保留 |

- 访问保留地址的结果见 §5.4。
- `dram.size` 由 `spec-arch` §8 定义。设备内存区域留到 64 GiB，容量改变时地址图不变。
- host 内存不在 DPA 空间中。HDMA 经描述符中的 host 总线地址访问 host 内存（`spec-host-dma` §3.2），其他 initiator 都不能访问 host 内存。

### 3.2 设备内存的交织

设备内存按 `dram.interleave_bytes` = 256 B 的粒度在 `dram.channels` 条通道（`spec-arch` §8，8 条）之间轮流分布：

```
通道号       c = PA[10:8]
Memory Tile  k = c >> 1          （Memory Tile k 位于坐标 (0, k)）
通道内地址      = { PA[39:11], PA[7:0] }
```

- Memory Tile k 连接通道 2k 和 2k + 1。
- 一段 **2 KiB 对齐**的 2 KiB 地址恰好覆盖全部 8 条通道各一次。大块顺序访问因此均匀地分到 4 个 Memory Tile，每个 Memory Tile 的出口平均承担约四分之一的带宽（推算）。
- NoC 上的请求不跨越 256 B 对齐的边界（§6.1），因此每个请求只落在一条通道、一个 Memory Tile 上。
- v0.1 采用简单取模。它可能让某些固定步长的访问集中到少数通道；性能模型如果显示出这类热点，再在后续版本中改为哈希交织。

### 3.3 DPA 出现在哪些接口中

| 接口 | 用途 | 定义 |
|---|---|---|
| HDMA 描述符的 DEV_ADDR | 搬运的设备侧地址 | `spec-host-dma` §3.2 |
| IDENTIFY 返回的 DEVMEM_BASE、DEVMEM_SIZE | 可分配给上下文的设备内存范围 | `spec-hdi` §9.2 |
| SET_CTX_REGION 的 BASE | 上下文可访问的区间 | `spec-hdi` §9.5 |
| BAR2 调试窗口的 WIN_BASE | 调试窗口指向的设备内存 | `spec-pcie` §7.5 |
| 管理 CPU 的本地地址 | DPA 映射在管理 CPU 本地地址空间中的位置 | `spec-mgmt-tile` §3.3 |
| 张量级指令的地址操作数 | 设备内存、其他 Tile 的 SRAM、本地窗口 | `spec-isa`（待写） |

## 4. Tile 窗口

### 4.1 编号与位置

坐标为 (x, y) 的 Mesh 位置，其窗口为：

```
窗口编号   n = y × 8 + x                         （x、y 均为 0 – 7）
窗口基址      = 0x10_0000_0000 + n × 0x100_0000  （16 MiB）
```

v0.1 的 Mesh 为 6 列 × 4 行（`spec-arch` §3.1），按上式计算的各位置窗口基址如下：

| y \ x | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 0 | M0：0x10_0000_0000 | 0x10_0100_0000 | 0x10_0200_0000 | 0x10_0300_0000 | 0x10_0400_0000 | PCIe：0x10_0500_0000 |
| 1 | M1：0x10_0800_0000 | 0x10_0900_0000 | 0x10_0A00_0000 | 0x10_0B00_0000 | 0x10_0C00_0000 | 管理：0x10_0D00_0000 |
| 2 | M2：0x10_1000_0000 | 0x10_1100_0000 | 0x10_1200_0000 | 0x10_1300_0000 | 0x10_1400_0000 | 预留：0x10_1500_0000 |
| 3 | M3：0x10_1800_0000 | 0x10_1900_0000 | 0x10_1A00_0000 | 0x10_1B00_0000 | 0x10_1C00_0000 | 预留：0x10_1D00_0000 |

第 1 – 4 列是 Compute Tile。x 为 6、7 或 y 为 4 – 7 的窗口编号保留给更大的 Mesh，v0.1 中按保留地址处理。

### 4.2 窗口内部

| 窗口内偏移 | 大小 | 内容 |
|---|---|---|
| 0x00_0000 – 0x7F_FFFF | 8 MiB | SRAM 区：从偏移 0 开始是该 Tile 的 SRAM，超出实际容量的部分保留 |
| 0x80_0000 – 0xFF_FFFF | 8 MiB | 寄存器区：布局由该 Tile 的规格定义 |

各类 Tile 的窗口内容：

| Tile | SRAM 区 | 寄存器区 | 是否是 NoC 的访问 target |
|---|---|---|---|
| Compute Tile | [0, `ct.sram_size`)（`spec-arch` §8） | Data Mover、同步计数器、指令队列状态、错误状态等，将由 `spec-compute-tile`（待写）、`spec-tile-sync`（待写）定义 | 是 |
| Memory Tile | 无，整个区保留 | DRAM 控制器配置、受保护区域、ECC 状态等，将由 `spec-dram`（待写）定义 | 是（只有寄存器区） |
| 管理 Tile | [0, `mgmt.sram_size`)；只有固件开放的区间可访问（`spec-mgmt-tile` §4.4） | 偏移 0 起是事件寄存器（`spec-mgmt-tile` §6.3），其他本地寄存器不对 NoC 开放 | 是（受限） |
| PCIe Tile | 无 | 无。PCIe Tile 的寄存器（包括 HDMA）只经 ML 访问，见 §4.4 | 否：整个窗口保留 |
| 预留位置 | 无 | 无 | 否：整个窗口保留 |

由此，管理 Tile SRAM 的 DPA `mgmt.sram_device_pa` = 0x10_0D00_0000（本文档拥有这一参数）。

### 4.3 Tile 本地窗口

- Compute Tile 内的部件（矩阵引擎、向量引擎、Data Mover、同步单元）访问 [0x20_0000_0000, 0x20_0100_0000) 中的地址 0x20_0000_0000 + o 时，访问的是本 Tile 窗口的偏移 o，与经全局窗口访问本 Tile 的效果相同。
- 本地窗口在 Tile 内部译码，不发到 NoC 上。Data Mover 把数据从本 Tile 搬到其他 Tile 时，目的地址必须写成目标 Tile 的全局窗口地址。
- 管理 CPU、HDMA、BAR2 调试窗口访问本地窗口，按保留地址处理（§5.4）。

### 4.4 HDMA 寄存器不在 DPA 空间中

PCIe Tile 不是 NoC 的访问 target。HDMA 的寄存器文件和 HIF 的其他内部寄存器只由管理 CPU 经 ML 访问，位于管理 CPU 本地地址空间中的 HIF 寄存器区（`spec-mgmt-tile` §3.3）。`spec-host-dma` §7.1 中的 `HDMA_BASE` 指该区的起始，是管理 CPU 的本地地址。

## 5. 访问权限

### 5.1 原则

每个 initiator 只能访问完成其职责所需的区域。权限分三级检查：

1. **源端区域检查**：每个 initiator 的 NI 按 §5.2 的矩阵检查请求的整个地址范围。这一级固定在硬件中，软件不能修改。
2. **target 端检查**：Memory Tile 检查受保护区域（§5.3），管理 Tile 检查 SRAM 的开放区间（`spec-mgmt-tile` §4.4）。
3. **上下文检查**：固件在执行命令之前，按上下文的区间表检查命令中的设备地址（`spec-hdi` §11.3）。

前两级由硬件执行：即使固件或程序生成了错误的地址，initiator 也不能越出 §5.2 规定的区域类型，也不能访问受保护区域。

**信任边界**：源端区域检查和 target 端检查不区分上下文。上下文之间的隔离由以下几点共同保证：

- 固件对命令中设备地址的检查（第 3 级）；
- 程序执行期间，Compute Tile NI 对设备内存访问的执行期区间检查（§5.2）。IDENTIFY 的 FEATURES[1] 为 1（`spec-hdi` §9.2），只表示这一项；
- v0.1 中 Compute Tile 阵列**同一时刻只执行一个上下文的程序**：固件按顺序执行不同上下文的 LAUNCH（`spec-hdi` §10.1 的规则 E3 允许设备按顺序执行）。因此 Compute Tile 之间经 SRAM 窗口和同步计数器的访问（不受区间约束）不会跨越上下文；
- 切换到另一个上下文的程序之前，固件等待上一个程序结束，按 `spec-clock-reset-power` §4.5 复位参与的 Compute Tile，并保证新程序读不到上一个上下文留在 Tile SRAM 中的数据（清零的机制将由 `spec-compute-tile`（待写）定义）。

不同上下文的数据搬运命令（COPY、FILL）可以与程序并发执行，它们由 HDMA 执行，受第 3 级检查约束。

### 5.2 区域权限矩阵

| initiator \ target | 设备内存 | 设备内存的受保护区域 | Compute Tile SRAM | Compute Tile 寄存器 | Memory Tile 寄存器 | 管理 Tile SRAM | 管理 Tile 事件寄存器 | 本地窗口 |
|---|---|---|---|---|---|---|---|---|
| 管理 CPU | 读写 | 读写 | 读写 | 读写 | 读写 | 本地访问，不经 NoC | 本地访问 | — |
| HDMA | 读写 | — | 读写 | — | — | —（描述符经 ML，不经 NoC） | — | — |
| BAR2 调试窗口 | 读写 | — | — | — | — | — | — | — |
| Compute Tile 的 Data Mover | 读写 | — | 读写 | 只有其他 Tile 的同步计数器 | — | 固件开放的区间 | 写 | 读写本 Tile |

"—"表示不允许。

- BAR2 调试窗口只能指向设备内存，与 `spec-pcie` §7.4 一致。
- Compute Tile 之间经同步计数器协调；可以写其他 Tile 的同步计数器，但不能访问其他 Tile 的其他寄存器。同步计数器在寄存器区中的位置将由 `spec-tile-sync`（待写）定义。
- **执行期区间检查**：程序执行期间的设备内存访问限制在本上下文带 X 权限的区间内（`spec-hdi` §11.3）。每个 Compute Tile 的 NI 带 `ct.exec_regions` = 8 个区间寄存器（与每个上下文的区间数 `hdi.ctx_regions` 相同），由固件在启动程序之前按该上下文带 X 权限的区间写入，程序执行期间不变（与 `spec-hdi` §9.5"新的区间配置只对之后开始执行的命令生效"一致）；Data Mover 对设备内存的请求在源端按这些区间检查，整个请求必须落在某一个区间内，否则按违例处理（§5.4）。区间寄存器只有管理 CPU 能写。

### 5.3 受保护区域

- 设备内存中最多可以设置 `dram.protected_regions` = 4 个受保护区域。每个区域以全局 DPA 的起始和大小描述，4 KiB 对齐。
- 每个 Memory Tile 各保存一份完整的受保护区域表，按全局 DPA 检查到达本 Memory Tile 的请求。由于请求不跨 256 B 边界（§6.1）而区域按 4 KiB 对齐，一个请求要么整个落在受保护区域内，要么整个落在外面。
- 大小为 0 的区域不起作用；区域可以重叠，效果为各区域的并集。
- 受保护区域只有管理 CPU 能访问；其他 initiator 访问时，Memory Tile 以错误响应返回，并记录出错地址和 initiator。
- **设置与锁定**：固件在初始化期间、启用 HDMA 和 Compute Tile 之前（`spec-mgmt-tile` §8.5），把同一份区域表写入全部 4 个 Memory Tile，读回确认，再依次锁定。锁定后直到设备复位都不能修改。由于设置在其他 initiator 启用之前完成，各 Memory Tile 的表短暂不一致不会造成保护缺口。寄存器的布局将由 `spec-dram`（待写）定义。
- 描述符环、固件代码已经放在管理 Tile 的 SRAM 中（`spec-host-dma` §3.1、`spec-mgmt-tile` §4.1）。固件在设备内存中没有必须保护的数据时，可以不设置受保护区域。

### 5.4 违例与保留地址的处理

访问保留地址、违反 §5.2 或 §5.3 时，整个请求以 REJECT 结束，不改变任何状态（不会只完成一部分），initiator 收到错误：

| initiator | 收到错误时 | 定义 |
|---|---|---|
| 管理 CPU | 访问错误异常 | `spec-mgmt-tile` §3.3 |
| HDMA | 描述符以 DEV_ADDR 失败 | `spec-host-dma` §8.1 |
| BAR2 调试窗口 | 读返回全 1，写丢弃，置 `ERR_STATUS.WIN_TARGET` | `spec-pcie` §7.6 |
| Compute Tile | Tile 进入错误状态，由固件处理 | `spec-compute-tile`（待写） |

以上都是 REJECT（§6.3 规则 0）。源端区域检查失败的请求不进入 NoC。target 端检查失败的请求还要报告给管理 Tile，汇聚方式将由 `spec-interrupt-ras`（待写）定义。

initiator 收到 FAULT 时，按上表的方式报告，并且无论 initiator 是谁，都要置位致命错误（`DEV_STATUS.DEV_FATAL`，`spec-pcie` §6.2），由 host 使用设备完全复位恢复。

## 6. 内存模型

### 6.1 访问粒度与原子性

| 层次 | 规定 |
|---|---|
| 单次访问 | 管理 CPU 的 load/store、对寄存器的访问：1、2、4、8 B，必须自然对齐 |
| 请求 | NoC 上的一次读或写：单次访问，或长度不超过 `noc.max_request_bytes` = 64 B 的突发。突发可以带字节使能。任何请求都**不得跨越 256 B 对齐的边界**，也不得跨越 §3.1、§4.2 的区域边界；initiator 负责拆分 |
| 不支持的大小或对齐 | 按违例处理（§5.4） |

- 自然对齐、不超过 8 B 的单次访问**不可撕裂**：target 把它作为一个不可分割的操作执行。一次读返回的各个字节都取自同一时刻 target 处的内容，不会与其他写交错；一次写的各个字节同时生效，其他读不会只看到其中一部分。不同大小的访问范围重叠时（例如 8 B 读与其中某 1 B 的写），按 target 执行它们的先后整体排序：8 B 读要么看到这 1 B 写之前的全部 8 字节，要么看到之后的全部 8 字节。
- 突发中每个自然对齐的 8 B 单元不可撕裂，整个突发不保证。
- 寄存器的访问宽度可能有更严格的限制，由各部件的规格定义。
- target 的 SRAM 带 ECC 时，不足一个 ECC 字的写由 target 做 RMW；target 必须把这次 RMW 与其他 initiator 对同一 ECC 字的访问串行化，使其对其他 initiator 表现为一次原子的写。
- v0.1 不提供 RMW 类的原子操作。Tile 之间的计数和同步用同步计数器（`spec-tile-sync`（待写））。

### 6.2 一致性

- 设备内部没有缓存：Compute Tile 只有 SRAM，管理 CPU 经 NoC 的访问不经缓存（`spec-mgmt-tile` §3.2）。每次访问都直接作用于 target，因此不需要缓存一致性协议。
- 设备与 host 内存之间的一致性见 `spec-pcie` §9。

### 6.3 顺序与可见性

以下规则对每个字节地址分别成立；访问的范围重叠即视为访问了相同的地址。

0. **请求的完成**：NoC 接受的每个请求，最终都恰好得到一个响应，响应是以下三种之一：
   - **OK**：请求已在 target 处执行完毕；
   - **REJECT**：请求没有产生任何效果，之后也不会产生（违例、保留地址、NI 隔离中的 target，§5.4、`spec-clock-reset-power` §4.5）；
   - **FAULT**：请求的效果未知，之后仍可能生效。FAULT 只在硬件故障时出现（例如 Tile 在 NI 隔离时停止响应，`spec-clock-reset-power` §4.5），收到 FAULT 的部件必须报告致命错误，设备只能经设备完全复位恢复。

   正常运行和受控的 NI 隔离过程中只出现 OK 和 REJECT。NoC 和每个 target 都不得丢弃请求或响应，并且必须保证前进：仲裁公平、缓冲有限、没有协议死锁。正常运行中，任何请求从发出到收到响应不超过 `noc.max_response_time` = 1 µs（设计目标，`spec-noc`（待写）必须以最坏拥塞下的分析或仿真证明；具体机制由它定义，不得弱化本条）。唯一的例外是冷复位、热复位和设备完全复位：Mesh 的全部端点同时复位，在途的请求和响应一并作废，没有未复位的一方在等待它们（`spec-clock-reset-power` §4.3）。

1. **写入序**：所有 initiator 对同一地址的写，在 target 处按一个唯一的全序生效，称为该地址的写入序。
2. **读**：读返回该地址的写入序中，在 target 处理这次读之前最后一个生效的写的值。
3. **同一 initiator、同一地址**：同一 initiator 对同一地址的访问按发出的顺序生效。因此一个 initiator 写后再读同一地址，读到的是自己写入的值，或写入序中更晚的值。
4. **其他情况不保证顺序**：同一 initiator 对不同地址的访问、不同 initiator 之间的访问，生效的先后与发出的先后无关。
5. **写的完成**：写在 target 处生效之后，target 才向 initiator 返回完成。完成之后 target 处理的任何读，返回的都是这次写的值或写入序中更晚的值。
6. **fence**：fence 等待**本 initiator**此前发出的全部请求都已完成，之后的请求才发出。fence 只覆盖发出它的 initiator：
   - 管理 CPU 的 `fence`（`spec-mgmt-tile` §3.4）只覆盖管理 CPU 自己的访问，不覆盖它让 Data Mover、HDMA 发出的访问；
   - HDMA 的写是否完成，以描述符的完成为准（`spec-host-dma` §5.3）；
   - Data Mover 的写是否完成，以它的完成通知为准（`spec-compute-tile`（待写）、`spec-tile-sync`（待写））；
   - Compute Tile 的 fence 指令将由 `spec-isa`（待写）定义。
7. **多播写**：在规则 0 的意义上，多播是对每个目的地各一个请求，每个目的地各自得到 OK、REJECT 或 FAULT，并分别满足规则 1 – 5。initiator 收齐全部目的地的响应后汇总：全部 OK 为 OK；任一目的地 FAULT 按 FAULT 处理；否则为部分 REJECT，被 REJECT 的目的地没有任何效果，其他目的地的写已经生效。initiator 如何向软件报告部分 REJECT，将由 `spec-isa`（待写）定义。
8. **跨 initiator 的同步**：
   - **释放**：生产者写完数据，执行 fence（规则 6），再通知消费者（递增同步计数器，或写事件寄存器）。
   - **获取**：消费者等待通知。等待同步计数器的操作具有获取语义：等待完成之后，消费者的后续请求才会发出。管理 CPU 以轮询读取通知时，必须在读到通知之后执行 `fence`，再读取数据。
   - 按此方式，消费者读到的数据是生产者在通知之前写入的值，或写入序中更晚的值。
   - 同步计数器只累加不丢失，适合传递"完成了几次"；管理 Tile 的事件寄存器只置位不排队（`spec-mgmt-tile` §6.3），只能表示"至少发生过一次"。

### 6.4 字节序

设备内部一律小端序，与 host 和 PCIe 一致。

## 8. 验收标准

| 编号 | 检查 |
|---|---|
| F1 | §3.1 中每个区域的地址都能译码到正确的 target；保留地址按 §5.4 处理 |
| F2 | §4.1 中每个 Tile 的窗口基址正确；SRAM 区超出实际容量的部分和 PCIe Tile、预留位置的窗口按保留地址处理 |
| F3 | 设备内存的交织符合 §3.2：2 KiB 对齐的 2 KiB 地址恰好覆盖 8 条通道各一次 |
| F4 | Tile 本地窗口：Compute Tile 内的访问指向本 Tile；本地窗口的地址不出现在 NoC 上；其他 initiator 访问时报错 |
| F5 | §5.2 中每个"—"格的访问都整个以 REJECT 结束，且不改变 target 的状态；跨 256 B 边界或跨区域边界的请求以 REJECT 结束 |
| F6 | 受保护区域：管理 CPU 可以访问，其他 initiator 以 REJECT 结束并记录；4 个 Memory Tile 的检查结果一致；锁定后不可修改 |
| F7 | 顺序：同一地址的写后读读到新值；多个 initiator 并发覆盖写同一地址时，所有读者看到的值都符合同一个写入序；fence 之后的访问看到 fence 之前本 initiator 全部写的结果 |
| F8 | 同步：生产者写数据后不执行 fence 就通知时，可以构造出消费者读到旧数据的情形（证明 fence 不可省略）；按 §6.3 规则 8 的释放与获取，消费者在任何乱序下都读到新数据 |
| F9 | 多播写在全部目的地生效后才完成；一个目的地失败时 initiator 收到错误 |
| F10 | ECC RMW 与其他 initiator 对同一 ECC 字的并发写串行化，不丢失任一次写 |
| F11 | 不可撕裂：8 B 读与对其中 1 B、4 B 的并发写，读到的 8 字节只能是写之前或写之后的完整内容 |
