## 1. 范围

本规格将定义 6 × 4 Mesh 的路由器、链路、NI、报文与消息类别、虚通道与信用、仲裁、顺序与 fence、错误与复位隔离（`spec-arch` §4）。当前版本只做第一步分析：`spec-address-map` §6.3 规则 0 要求"正常运行中，任何请求从发出到收到响应不超过 `noc.max_response_time` = 1 µs，`spec-noc` 必须以最坏拥塞下的分析或仿真证明"。本文把一类请求的路径拆成各段预算，标出哪些已有依据、哪些缺失，并给出在写明的条件下成立的反例。

已由其他规格确定、本文只引用的事实：

| 事实 | 来源 |
|---|---|
| 布局：Memory Tile 在第 0 列，Compute Tile 在第 1–4 列，PCIe Tile (5,0)，管理 Tile (5,1) | `spec-arch` §3.1 |
| 链路宽度 `noc.link_bytes_per_cycle` = 64 B/周期 | `spec-arch` §4 |
| 路由器与全部 NI 在 `clk_core`（`clock.core_freq` = 1 GHz） | `spec-clock-reset-power` §3.2 |
| CDC 只在 Mesh 的边界：PCIe Tile 的 NI（`clk_pcie` ↔ `clk_core`）、管理 Tile 的 NI（`clk_mgmt` ↔ `clk_core`）、Memory Tile 内部（`clk_core` ↔ `clk_ddr`），都用异步 FIFO | `spec-clock-reset-power` §3.3 |
| NoC 上的 initiator：管理 CPU、HDMA、BAR2 调试窗口、16 个 Compute Tile 的 Data Mover | `spec-address-map` §1.3 |
| 每个请求恰好一个响应；NoC 与 target 不丢弃请求、仲裁公平、缓冲有限、没有协议死锁 | `spec-address-map` §6.3 规则 0 |
| 设备内存按 256 B 在 8 条通道之间交织，通道号 c = PA[10:8] | `spec-address-map` §3.2 |

## 2. 预算分解（模板，尚非上界证明）

以 Compute Tile 或 HDMA 读设备内存为例，从 initiator 发出请求到收到响应。本节只覆盖这一类请求；写请求、寄存器访问和其他 target 留到后续版本，规则 0 对它们同样适用。

| 段 | 符号 | 依据与现状 |
|---|---|---|
| 源 NI：区域检查、组包、注入排队 | T_src | 待定：NI 的流水级数与注入队列深度（G-N2）。"发出"的计时起点（进入注入队列之前还是之后）也待定义 |
| 源端 CDC（HDMA、BAR2 经 PCIe Tile；管理 CPU 经管理 Tile） | T_cdc,src,req、T_cdc,src,rsp | 异步 FIFO 的同步级数待定（G-N2）；两个方向的目的时钟不同，分别计 |
| Memory Tile 内的 CDC | T_cdc,mem,req、T_cdc,mem,rsp | 同上；`clk_ddr` 的频率由 PHY 决定（`spec-clock-reset-power` §3.2） |
| 逐跳传输 | 请求、响应各 H × (P_r + 1) 个 `clk_core` 周期 | H：XY 路由的跳数，Compute Tile 到 Memory Tile 最多 4 + 3 = 7 跳，PCIe Tile (5,0) 到 M3 (0,3) 为 5 + 3 = 8 跳（推算）；P_r：路由器流水级数，待定（G-N2） |
| 序列化 | T_ser,req、T_ser,rsp | 读请求只有报文头，读响应还带数据（64 B 在 64 B/周期的链路上占 1 个周期）；报文格式待定 |
| 各跳的仲裁与反压 | T_arb | 取决于仲裁算法、虚通道和下游的排空速度；下游最终由 target 的服务速度决定。与 T_queue 可能重叠，不能简单相加 |
| target 的排队与服务 | T_queue + T_svc | DRAM 的行命中、行冲突、读写切换、刷新、bank 并行与重排（§3）；核心时序无依据（`spec-dram` G1） |

待去重的候选分解项为 T_src、T_cdc,src,req、T_ser,req、请求的逐跳传输 H·(P_r + 1) ns、T_cdc,mem,req、T_arb、T_queue、T_svc、T_cdc,mem,rsp、T_ser,rsp、响应的逐跳传输、T_cdc,src,rsp；最终要求是端到端时间 T ≤ 1 µs。各项的最坏值、它们之间的重叠，以及"N 个请求排在前面"对应的服务模型，都要在后续版本中定义后才能构成证明。

## 3. 条件性反例：不约束同一通道的在途请求时 1 µs 不成立

用到的数字（`spec-dram` §3）：

- **数据总线占用**：x16、8533 Mb/s 的通道每传 64 B 至少占用数据总线 64 ÷ 17.066 GB/s ≈ 3.750 ns（推算），这是不计命令、读写切换和其他开销时的下限。
- **刷新**：Y4BM（12Gb die）的 tRFCab = 280 ns（S2 p.9 Table 4，已核对）；all-bank 刷新期间，被刷新的 rank 不能服务。同一通道的其他 rank 能否同时服务、是否会连续安排多次刷新，取决于器件组织（`spec-dram` G2）和刷新策略，尚未确定；一次 tRFCab 也不是刷新策略的最坏阻塞上界。

**反例 A**。条件：采用上述候选器件；208 个各 64 B 的读请求都已发出，它们覆盖互不重叠的 64 B 区间，全部要从同一条通道的同一个 rank 取数据；该 rank 恰在此时开始一次 all-bank 刷新，这些请求的数据都尚未取回，刷新结束后必须经这条通道传输合计 208 × 64 B。那么即使忽略 NoC、CDC 和全部 DRAM 命令开销，这 208 个请求全部完成至少需要 280 + 208 × 3.750 ≈ 1060 ns（推算），所以至少有一个请求从发出到收到响应超过 1 µs，与它们之间的服务顺序无关。

这些条件在目前的设计中都没有被排除：

- 通道号只由 PA[10:8] 决定，地址相差 2 KiB 的倍数即落在同一条通道（`spec-address-map` §3.2），交织不能阻止合法程序把请求集中到一条通道；同一 rank 则取决于通道内的映射（`spec-dram` G4）；
- 落到同一条通道的在途请求总数尚未定义有依据的全局上限：HDMA 的在途上限 32 是假定值（`gem5-ext/README.md` 理想化 #10c），16 个 Data Mover 和管理 CPU 的上限尚未定义。例如 16 个 Data Mover 各有 11 个在途读，加上 HDMA 的 32 个，共 208 个；"11 个"只是为了构造反例的假设。

因此，反例 A 说明的是：当前的契约没有排除这种情形，设计必须加以约束，或者修改契约（§4 D1）；它不证明最终的 GW100 必然违反 1 µs。只按剩余数据带宽估计，总量约 192 个请求（720 ÷ 3.750，量级）就会用完预算；这只是下界，不能直接作为准入额度，它没有计入首次读的延迟、命令开销、NoC 与 CDC。

**行冲突（条件性的量级示例）**。同一 rank、同一 bank 中访问不同行的 k 个请求，至少需要 k − 1 个连续 ACT 的间隔（每个不短于 tRC），再加上最后一次 ACT 到数据返回的延迟。LPDDR5X-8533 的 tRC 没有依据（`spec-dram` G1）；若按上游 LPDDR5 线索的 tRAS + tRP = 42 + 18 = 60 ns 估计，扣除一次 280 ns 的刷新后，k 约十余个就会用完 1 µs。这只说明行冲突可能比纯带宽更早用完预算，不能作为已证明的配置。另外，持续优先调度行命中、又没有其他保障的控制器，可能让一个行冲突的请求长时间等待。

**由此得到的要求**：要证明 1 µs（或任何上界），本规格必须给出：

1. 发往同一条通道、同一个 rank 或 bank 的请求的流量与突发约束（例如各 initiator 在途上限之和的上限，或 target 的准入控制）；若用准入控制，要定义计时起点，说明在源 NI 等待准入的时间是否计入，并保证发往其他 bank、其他通道的请求不会因此被无限期阻塞；
2. DRAM 调度的有界等待：对任一合法请求，给出可由配置和流量约束计算的最大等待时间（或最大被超越次数），并证明它不随持续到来的请求无限增长（候选实现：按年龄的上限、有界轮转、服务配额）；
3. 刷新阻塞的上界（all-bank 或 per-bank、可推迟的次数、多 rank 时的安排）；
4. `spec-dram` G1 的核心时序，才能算出 T_svc 的最坏值；
5. 在以上约束下的端到端响应时间的证明（分析，或分析加最坏情形的仿真）。

反例中的下界只能排除方案，不能直接推出足够的额度；额度要由第 5 项的完整上界确定。

**D1：`noc.max_response_time` 的处置（待用户决定）**。三个方案都要满足 §3 的第 1–3、5 项，区别在于上界怎样表述：

| 方案 | 内容 | 影响 |
|---|---|---|
| 保持 1 µs | 依据完整的最坏上界确定各项额度 | 1 µs 可能要求更严格的资源预留与流量约束，例如较小的在途额度；额度过紧会限制带宽：每条通道维持满带宽约需 17.07 GB/s × 往返时间 的在途数据，往返时间按 150 ns 的示例假设约为 2.6 KB、40 个 64 B 请求（推算，150 ns 不是已核对的往返时间，带宽时延积也不是最坏时延的证明） |
| 放宽上界 | 机制确定、G1 有依据后，按最坏分析重新取值（可能是若干微秒） | 要同步修改 `spec-address-map` §6.3 规则 0、依赖它的超时（`spec-clock-reset-power` §4.5）和 `spec-pcie` §11.2 P4 |
| 分成几份预算 | 传输（NoC 本身）、target 服务（由 `spec-dram` 等按 target 类型给出）、故障检测（超时按两者之和的若干倍）分别定义 | 传输部分同样需要拥塞下的证明；规则 0 要改成按 target 类型的上界，同样要同步修改上述规格 |
