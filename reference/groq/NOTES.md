## 架构要点

**确定性与编译器**（TSP p.3、p.7–8）
- 硬件里没有仲裁器，也没有 cache，执行时间完全可预测。
- ISA 把每条指令的时序暴露给编译器：功能延迟 d_func 表示输出何时出现在流上；指令-操作数偏移 d_skew 表示指令派发时刻与操作数到达时刻的关系。
- NOP 带 16 位重复计数，编译器用它精确控制两条指令之间的间隔。
- 程序开头用 Sync/Notify 做一次全片 barrier（35 个周期），之后不再需要同步。

**存储**（TSP p.6、p.8）
- 全局地址空间按 slice 均匀分布；bank 位暴露给编译器，由编译器安排 bank 并发。
- 支持直接寻址，也支持用流的内容做间接寻址（gather / scatter）。

**可靠性**（TSP p.6；HC34 p.57–60）
- 每 128 bit 数据配 9 bit SECDED ECC，在生产方生成，由消费方在使用前检查；同一套 ECC 覆盖 SRAM 和流数据通路。
- 纠正过的错误记录在 CSR 里，可以作为芯片老化的早期信号。
- 每个 superlane 的 45 个流寄存器站点都有 SECDED 保护。
- NaN 和 Inf 可能来自软错误，因此要事先规定好算术异常的处理方式。

**确定性对设计验证的好处**（HC34 p.55）
- 功能单元的输入输出都经过定义明确的流寄存器站点，可以用"假设-保证"方式分模块验证。

**多芯片**（TSM p.2–5；HC34 p.39–52）
- 软件调度的 Dragonfly 网络，链路上没有反压，由软件安排每条链路上的传输。
- 包就是一个 320 B 的向量，头尾 flit 的开销只有 2.5%，没有硬件流控和虚通道。
- 每颗芯片有一个自由运行的硬件对齐计数器（HAC），配合 DESKEW / RUNTIME_DESKEW 指令，在异步时钟的芯片之间维持统一时间。

## 对我们的启示

| 我们的设计问题 | 借鉴点 | 对应文档 |
|---|---|---|
| 调度方式 | 全静态调度要求延迟完全确定，我们的权重在 DRAM，前提不成立；只在 Tile 内部、延迟确定的路径上，可以借鉴把时序暴露给编译器的做法 | SPEC-230 |
| 功能单元串接 | 矩阵单元的结果直接流进向量单元，不写回 SRAM（例如矩阵乘 → 反量化 → 激活） | SPEC-200 / 210 / 220 |
| 累加精度 | 长点积只在最后舍入一次 | SPEC-240 |
| ECC | 生产方生成、消费方检查，一套 ECC 覆盖存储和数据通路；纠错次数记入 CSR | SPEC-340 / 350 |
| 良率冗余 | 预留备用单元并对编译器隐藏；我们可以在 Tile 或 cluster 级别做同样的事 | SPEC-100 |
| 异常处理 | 事先规定 NaN 和 Inf 的处理策略 | SPEC-240 / 340 |
| 设计验证 | 确定的生产者-消费者接口可以简化 RTL 验证和 gem5 校准 | DOC-004 |

## 存疑与待核对

- 两篇论文都写于 LLM 流行之前，没有 LLM 的数据。Groq 后来做的 LLM 推理服务依靠数百颗芯片把模型全部放进 SRAM，和端侧单芯片的场景完全不同。
